# Debian package

`npm run build:deb` produces `dist-deb/paseo_<version>_<arch>.deb`: the daemon,
the `paseo` CLI, and the browser UI the daemon serves on its own port.

It is one process. `npm run dev:app` is an Expo development server, not a
runtime component — in a release build the front end is exported to static
files and the daemon serves them, so there is nothing to start alongside it.
[docs/docker.md](docker.md) packages the same thing as a container; pick the
deb when you want the daemon on the host with access to your own checkouts.

## Building

```bash
npm run build:deb                 # full build, ~10 min
npm run build:deb -- --skip-pack  # reassemble from dist-deb/packs, seconds
```

Options: `--version`, `--arch`, `--maintainer`, `--out`.

The build packs the seven workspace tarballs and hands them to a single
`npm install -g --prefix`. Both halves of that matter:

- **Packing produces the front end.** `@getpaseo/server`'s `prepack` runs
  `build:daemon-web-ui`, and its `files` ships `dist/server`. Nothing in the
  deb build exports the web app itself.
- **One `npm install` command, not seven.** The packages depend on each other
  by exact version and those versions are published. Installed one at a time,
  npm would fetch the siblings from the registry and you would ship released
  code instead of your working tree.

The package is architecture-specific because `node-pty` and `sherpa-onnx-node`
carry compiled binaries. Build on the architecture you will install on.

Node is not bundled; the package depends on `nodejs (>= 22)`. Both native
modules are N-API addons, whose binary interface is stable across Node major
versions, so the distro's Node runs binaries built against a different one.

Agent CLIs are not included. Install Claude Code, Codex, OpenCode or Pi
separately — bundling them would tie Paseo releases to theirs.

## Choosing a unit

The package installs two units and enables neither. They differ in which user
the daemon runs as, which decides what it can see:

|                                     | `systemctl --user enable --now paseo` | `sudo systemctl enable --now paseo` |
| ----------------------------------- | ------------------------------------- | ----------------------------------- |
| Runs as                             | you                                   | the `paseo` system user             |
| Home                                | `~`                                   | `/var/lib/paseo`                    |
| Config                              | `~/.config/paseo/paseo.env`           | `/etc/paseo/paseo.env`              |
| Sees your checkouts and `~/.claude` | yes                                   | no                                  |

Use the user unit on a machine where you work on the code yourself — it is what
your two terminals were already doing. Add `loginctl enable-linger $USER` so it
survives logout. Use the system unit for a dedicated box where the agents get
their own home.

## Remote access

`postinst` generates `/etc/paseo/paseo.env` with a random `PASEO_PASSWORD` and
`PASEO_LISTEN=0.0.0.0:6767`. The user unit reads no such generated file; copy
`/usr/share/paseo/paseo.env.example` to `~/.config/paseo/paseo.env` and set a
password yourself.

Never leave `PASEO_PASSWORD` empty on a non-loopback listen address. The daemon
accepts unauthenticated control connections from anyone who can reach it, and
those connections drive agents that can write to your disk.

Reaching the daemon by DNS name needs `PASEO_HOSTNAMES`. IP addresses and
`localhost` are allowed by default and names are not, so the first symptom is
`403 Host not allowed`. Reverse proxy configuration is the same as the
container's — see [docs/docker.md](docker.md#reverse-proxies).

See [SECURITY.md](../SECURITY.md) for the daemon trust model.

## Packaging layout

`packaging/debian/` holds the control template, the two units, the env template
and the maintainer scripts; `scripts/build-deb.mjs` assembles them.

The env file is generated by `postinst` rather than shipped as a conffile,
because it carries a per-machine password — there is no packaged default for
dpkg to diff against on upgrade. `purge` removes `/var/lib/paseo`; `remove`
keeps it.

The units deliberately set no `ProtectHome=` or `ReadOnlyPaths=`. Agents read
credentials from the home directory and write to the checkouts under it.
